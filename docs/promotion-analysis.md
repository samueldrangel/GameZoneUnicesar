1. Class Hierarchy and PolymorphismQuestion: The three promotions have different calculation rules but share common attributes and behaviors. How is this situation reflected in the design of the class hierarchy? What mechanism of Object-Oriented Programming allows each promotion type to calculate its discount differently without the rest of the system needing to know the concrete types?   
Answer: This is reflected by creating an abstract base class named Promotion in the model package, which contains shared attributes such as id, name, startDate, and endDate, along with common methods like isActive(LocalDate date). The three promotion types (PercentageDiscount, CategoryDiscount, and BulkPurchaseDiscount) extend this base class to inherit common behavior.   The Object-Oriented Programming mechanism that enables different discount calculations is polymorphism combined with method overriding (@Override). The base class defines an abstract method calculateDiscount(Sale sale). Each subclass provides its own specific implementation. Consequently, higher-level services can invoke calculateDiscount on any Promotion reference without knowing its concrete class at compile-time.  

2. Abstract Base Class and Method DeclarationQuestion: The base class Promotion cannot implement the discount calculation method because each type has a different logic. How is this method declared in the base class, and what does this declaration guarantee regarding the subclasses?   
Answer:The method is declared in the base class as an abstract method without a body:Javapublic abstract double calculateDiscount(Sale sale);

This declaration guarantees two main structural rules:It forces the base class Promotion to be declared as abstract, preventing direct instantiation of a generic promotion.   It establishes a mandatory contract: every concrete subclass extending Promotion must provide a concrete implementation of calculateDiscount(Sale sale). If a subclass fails to implement it, the compiler will raise a compilation error.

3. Business Rule Location and Layered ArchitectureQuestion: The business rule states that only the promotion with the highest discount is applied. Where is this selection logic located, and why is this location coherent with the layered architecture principle? Why should this logic NOT be in the Sale class or the console menu?   
Answer: This selection logic is located inside the PromotionService class (specifically within the findBestPromotionFor(Sale sale) method).   Coherence with Layered Architecture: The service layer is responsible for processing business rules, orchestrating complex domain logic, and coordinating multiple entities. Evaluating multiple active promotions against a sale to select the maximum discount is purely a business domain policy.   Why NOT in Sale: The Sale class belongs to the model layer. Its responsibility is to represent a single sale data structure, not to query external promotion repositories or evaluate system-wide active campaigns. Putting this logic in Sale would violate the Single Responsibility Principle (SRP) and couple the model layer with promotion repositories.   Why NOT in ConsoleMenu: The ui layer is strictly intended for user interaction, input capturing, and output formatting. Placing business calculation rules in the UI violates the separation of concerns, leads to code duplication, and makes automated testing impossible.   

4. System Impact on Existing Code (Sale and generateReceipt)Question: What modifications are necessary in the Sale class and in the generateReceipt method so that the receipt shows the applied discount? Do these modifications break any existing behavior in the system?   
Answer:The necessary modifications to the Sale class are additive and non-breaking:   Adding two new private fields: appliedPromotionName (String) and discountAmount (double), along with their respective getters and setters.   Modifying generateReceipt() to format and display the breakdown: Subtotal, Discount Applied (including promotion name), and Final Total (Subtotal - Discount).   These modifications do not break existing behavior. If no promotion applies, appliedPromotionName remains "None" (or empty) and discountAmount defaults to 0.0, preserving backward compatibility for normal sales calculations while cleanly extending receipt generation functionality.    

5. Validation Location for Active PromotionsQuestion: Active promotions are determined by comparing the current date with the start and end dates of each promotion. Where is this validation performed (in the Promotion class, in PromotionService, or in both)? Justify.

Answer:This validation is performed in both classes, respecting encapsulation and delegation:   In Promotion: The Promotion class encapsulates its own date state and implements the domain helper method isActive(LocalDate date): boolean. It calculates whether a given date falls within startDate and endDate.   In PromotionService: The service layer coordinates the collection of promotions. Methods like listActivePromotions() and findBestPromotionFor(Sale sale) call promotion.isActive(currentDate) while filtering the list of all stored promotions.   This separation ensures high cohesion: Promotion knows how to check if it is active for a given date, whereas PromotionService knows when and on which dataset to apply that filter.
